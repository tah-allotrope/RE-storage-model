2. Real-Format Excel Loaders

Production Excel files don't follow a simple flat layout. Three new loader capabilities were added to bridge the gap between the real file format and the Python model:

Loader Function Sheet What It Handles
load_assumptions_from_cells() Assumption Multi-region cell-based layout — parameters scattered across non-contiguous blocks rather than a single table
load_hourly_data() (enhanced) Data Input Auto column rename: SimulationProfile_kW → simulation_profile_kw, handles mixed-case headers
load_degradation_table() (enhanced) Loss Header row detection, column rename: PV → pv_factor, Battery → battery_factor_with_replacement
load_financial_params_from_cells() Assumption Reads capex, debt tenor, interest rate, DSCR target, tax rates from named cell regions
load_tariff_rates_from_cells() Assumption Reads off-peak / standard / peak rates from tariff block, maps to TimePeriod enum

3. extract_excel_kpis.py — Reference KPI Extraction Script

A one-time (or post-Excel-change) script that reads the pre-calculated values directly out of Excel using openpyxl data_only=True and saves them to JSON reference files. This is the ground truth that regression tests compare against.

4. The Regression Test Suite

Three parametrized test methods that auto-discover project pairs from disk:

Test Method What It Checks KPIs Compared Status
test_all_kpis Full pipeline — all available KPI tiers All 11 KPIs in tolerance map PASS
test_physics_layer Isolates solar gen + SoC tracking only calc_solar_gen_sum_kwh, calc_soc_min_kwh, calc_soc_max_kwh PASS
test_financial_kpis Final financial outputs only project_irr, equity_irr, unlevered_irr, npv_usd, dscr_min PASS
Why Three Separate Tests? Each test layer creates a diagnostic ladder. If test_physics_layer fails but test_financial_kpis passes, the bug cannot be in the physics layer. If both physics and aggregation pass but financials fail, the bug is isolated to the waterfall/debt/metrics modules. This avoids wasting time investigating the wrong layer.

5. Tolerance Tiers

Different KPI types have different acceptable error margins, defined in AGENTS.md §4.3:

🏦

±0.001 absolute

6. Bug Fixed During Week 7 — PV2BESS Mode 0

Root Cause: PV-to-BESS charging Mode 0 was not sending all surplus to battery
BEFORE: Mode 0 treated surplus the same as Mode 1, only charging within the configured time window
AFTER: Mode 0 correctly sets min_direct_pv_share=1.0 and active_pv2bess_share=1.0 — all surplus charges BESS at any hour, regardless of time window

This fix was caught because the physics regression test (calc_solar_gen_sum_kwh, calc_soc_max_kwh) diverged from the Excel reference values. Without the regression harness, this mode-specific error would have propagated silently into settlement and financial outputs.

📋 Key Tests Explained

Battery: Property-Based SoC Bounds Test (Hypothesis)

Rather than hand-crafted examples, test_battery.py uses the Hypothesis library to generate hundreds of random valid inputs and verify that SoC never violates [0, max_capacity]:

from hypothesis import given, strategies as st

@given(
    soc=st.floats(min_value=0, max_value=200),
    charge_kw=st.floats(min_value=0, max_value=100),
)
def test_soc_always_in_bounds(soc, charge_kw):
    result = update_soc(soc, charge_kw, max_capacity_kwh=200, ...)
    assert 0 <= result <= 200

Financial: Debt Sizing via scipy.optimize

The amortization test verifies that size_debt_for_dscr() numerically solves for the maximum debt amount where the minimum annual DSCR stays at or above the target:

ebitda = pd.Series([1300.0, 1200.0], index=[1, 2])
debt_amount, schedule = size_debt_for_dscr(
    ebitda_series=ebitda,
    interest_rate_pct=10.0,
    tenor_years=2,
    target_dscr=1.3,
    initial_guess_usd=1000.0,
)

dscr = ebitda / schedule["total_debt_service_usd"]
assert dscr.min() >= 1.3 - 1e-6  # DSCR constraint satisfied

Regression: KPI Comparison Logic

Each KPI uses a mode-specific comparison. IRR uses absolute difference (percentage points matter more than relative), while energy and revenue use relative difference (the numbers are large, so a fixed absolute tolerance would be too tight):

if mode == "abs":
    diff = abs(actual - expected)
    passed = diff <= tolerance   # e.g. IRR: |0.1421 - 0.1423| <= 0.0001

elif mode == "rel":
    diff = abs(actual - expected) / abs(expected)
    passed = diff <= tolerance   # e.g. energy: |72541200 - 72544000| / 72544000 <= 0.0001

Integration: Leap Year Aggregation

A subtle edge case — 2024 is a leap year with 8784 hours. The monthly aggregation must handle the extra February 29 row without breaking the 12-month output shape or total sums:

datetimes = pd.date_range("2024-01-01", periods=8784, freq="H")
# 8760 hours (normal year) + 24 extra (Feb 29)

monthly = aggregate_hourly_to_monthly(hourly, demand_reduction_target_ratio=0.0)
assert len(monthly) == 12                                  # still 12 months
assert monthly["bau_grid_expense_usd"].sum() == pytest.approx(8784.0)  # all hours counted

🏗 Architectural Patterns

1. Layered Architecture with One-Way Data Flow

Data flows strictly downward through layers. No layer imports from a layer above it. This makes the regression harness possible — you can validate each layer independently.

Layer Order core → inputs → physics → settlement → aggregation → financial → validation

2. Immutability for Physics State

BatteryConfig is a @dataclass(frozen=True) — parameters cannot be mutated mid-simulation. BatteryState is a NamedTuple — each timestep returns a new state rather than mutating the old one. This eliminates an entire class of subtle bugs where state from one timestep leaks into the next.

3. Dual API (Scalar + Vectorized)

Every physics function has two versions: a scalar version for clarity and step-by-step debugging, and a vectorized NumPy version for performance over 8760-row hourly datasets. Unit tests verify both match for identical inputs.

4. Defensive Input Validation at System Boundaries

Inputs are validated using Pydantic (extra="forbid") at the loader boundary. Within the physics layer, negative values raise explicit domain exceptions (SoCBoundsError, EnergyBalanceError) rather than producing silently wrong results.
