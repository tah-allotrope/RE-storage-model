01 / Executive Summary

Executive Summary

What Was Built

A dppa_topology parameter ("onsite" / "offsite") that controls which revenue streams are active per pipeline run. The parameter flows through the entire stack: public API, settlement engine, scenario runner, sensitivity analysis, and CLI assessment script.

Why It Matters

Previously all pipeline runs treated every project identically — grid savings and demand charge savings were always computed regardless of physical topology. Offsite (virtual PPA) projects had overstated economics. Now the assessment workbook can compare onsite vs offsite economics side-by-side.

02 / Background & Objective

Background & Objective

The DPPA assessment gap analysis (GAP-02) identified that the model could not distinguish between onsite (behind-the-meter) and offsite (front-of-meter / virtual PPA) project configurations. Onsite projects benefit from grid savings (reduced utility bills) and demand charge reduction, while offsite projects sell all generation to the grid under a CfD structure — grid savings and demand charge savings do not apply.

The objective of this sprint was to add a dppa_topology parameter that correctly masks revenue streams based on topology, thread it through the entire pipeline and scenario infrastructure, and enable the assessment workbook to show both configurations side-by-side.

03 / Inputs & Scope

Inputs & Scope

In Scope

  • dppa_topology parameter on run_full_model() and run_model_from_json()
  • Topology masking in _run_settlement(): zero out grid savings for offsite
  • Topology masking on demand charge savings for offsite
  • Topology parameter on run_all_scenarios() and run_sensitivity_for_values()
  • --topology CLI flag on assessment script ("onsite", "offsite", "both")
  • Dual-topology workbook generation with separate assessment/comparison sheets

Out of Scope

  • Changing BESS dispatch strategy per topology (user decision: keep same dispatch)
  • Two-component tariff integration (Sprint 4)
  • Wind generation support
  • Factory-side NPV
  • Dispatch chart embedding (Sprint 3)
  • Go/no-go assessment logic (Sprint 3)
04 / Assumptions & Constraints

Assumptions & Constraints

Key Assumptions

  • ASM-001: Onsite topology includes grid savings and demand charge savings; PPA options 1 & 2 are natural comparisons
  • ASM-002: Offsite topology zeros grid savings and demand charge savings; PPA options 3 & 4 are natural comparisons
  • ASM-003: Topology flag does NOT change physics — dispatch remains identical between topologies
  • DEC-001: Topology is a string literal, not an enum. Values: "onsite", "offsite"

Constraints

  • CON-001: Sprint 1 (Excel writer + payback metrics) must be complete before dual-topology workbooks can be generated
  • CON-002: No Excel fixture available for full end-to-end topology tests — 5 tests currently skipped
05 / Methodology

Methodology

The implementation followed a three-phase approach: (1) add topology to the pipeline core, (2) thread it through the scenario infrastructure, and (3) wire it into the CLI and workbook output. Each phase was independently tested and committed.

The key design decision was to keep the same physics dispatch for both topologies (per user direction on Q-001). This means only the revenue masking layer is affected — the solar generation profile and battery dispatch remain identical. This is the correct approach because dispatch strategy is independently controlled by strategy_mode in the input assumptions.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

PHASE-01: Pipeline Topology

Files: src/re_storage/pipeline.py, tests/unit/test_pipeline_topology.py

Added dppa_topology to both public API functions (run_full_model and run_model_from_json), and wired it through _run_settlement(). Applied topology masking: zero grid savings in settlement output and zero demand charge savings after aggregation. Validation raises ValueError for values outside {"onsite", "offsite"}. Also added demand charge savings computation to the JSON pipeline path via cp_demand_vnd_per_kw.

PHASE-02: Scenario Runner

Files: scenarios/runner.py, scenarios/sensitivity.py, tests/unit/test_scenarios_topology.py

Added dppa_topology parameter to run_all_scenarios() and run_sensitivity_for_values() with validation. Topology is passed through to every pipeline call within those functions. Three tests cover invalid topology rejection and parameter acceptance in the scenario runner.

PHASE-03: Dual-Topology CLI

Files: scripts/generate_dppa_assessment.py, tests/integration/test_dppa_assessment_script.py

Added --topology CLI flag with values "onsite", "offsite", or "both" (default). When "both", the script runs the pipeline twice (onsite + offsite), produces separate assessment sheets ("Assessment (Onsite)", "Assessment (Offsite)"), separate comparison sheets per topology, and shared Cover/Sensitivity/Assumptions sheets. Integration tests verify each topology mode produces the expected sheets.

07 / Findings & Recommendation

Findings & Recommendation

The implementation is sound for the defined scope. Key findings:

  • Topology masking is clean: Zeroing grid savings and demand charge savings in the settlement/aggregation layers is proven by the existing test suite — onsite default preserves all prior regression outputs.
  • JSON path parity improved: The JSON pipeline path previously did not compute demand charge savings. This sprint added that computation via cp_demand_vnd_per_kw, improving parity with the Excel path.
  • Dual-topology workbook works: Running 2 topologies × 4 PPA options = 8 pipeline runs produces a comprehensive assessment. Execution time (~4-8 min) is acceptable for a deliverable.
  • Sprint 1 foundation held: The Sprint 1 Excel writer and payback metrics were stable — no regressions from the topology changes.

Recommendation: Proceed to Sprint 3 (go/no-go logic, dispatch charts, branding) as planned. The topology work is verified and production-ready.

09 / Risks / Open Questions

Risks / Open Questions

Risks

  • RISK-01: Offsite topology with Options 1/2 (Bundled/Separate) produces lower revenue — the assessment should note this in a Methodology sheet rather than hiding it.
  • RISK-02: Running 2 topologies × 4 scenarios × pipeline = 8 full runs takes ~2-4 minutes. The CLI script currently logs progress but has no visual progress indicator.
  • RISK-03: No Excel fixture for topology tests — 5 tests are skipped. If the Excel fixture has different column names, the topology masking may not apply correctly.

Open Questions

  • Should offsite topology support a different sensitivity variable set (e.g., exclude grid-related variables)?
  • Should the Cover sheet show both topology's KPIs side-by-side when topology="both"?
  • Is there a client requirement for offsite topology dispatch strategy to differ (pure arbitrage vs peak shaving)?
