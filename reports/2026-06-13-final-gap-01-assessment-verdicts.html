01 · Executive Summary

The answer, first

A gap analysis of the RE-Storage web tool (a browser interface for the Vietnam Solar + BESS financial model) found its single highest value-per-effort shortfall: the model produces a structured investment recommendation — assess_project() grades Equity IRR, DSCR, NPV, and Payback and returns an overall GO / CAUTION / NO-GO — but the website threw that recommendation away and showed only raw numbers. Users had to interpret the verdict themselves.

02 · Background & Objective

Why this mattered now

RE-Storage simulates solar-plus-battery projects in Vietnam and outputs project-finance metrics (IRRs, DSCR, NPV, payback). A web interface — benchmarked against NREL's REopt — already existed, with input forms, a KPI dashboard, charts, scenario comparison, and sensitivity analysis. But a REopt-style tool's headline is a recommendation, and ours was missing it despite the logic existing in the codebase since Sprint 3. The objective: close that gap so a non-expert can open the dashboard and immediately see whether a project clears its investment hurdles, and why.

05 · Methodology

How the work progressed

Test-driven, one phase at a time, with a report, commit, and push at each phase boundary. PHASE-01 added the verdict to the backend response; PHASE-02 rendered it. Because both run endpoints already share one serialisation function, a single backend change covered both the Excel-upload and structured-form paths.

06 · Phase-by-Phase Analysis

PHASE-01 · Backend verdict shipped

  • Hardened against missing data — a null payback degrades to FAIL instead of crashing.

07 · Findings & Recommendation

What we found, what we advise

Findings

  • The highest-impact gap was pure presentation, not computation — the recommendation existed but was discarded.
  • Reusing the model's own grading function eliminated the largest risk: a website verdict that contradicts the spreadsheet.
  • Shared serialisation meant one change lit up both run paths.

Test growth (TDD)

Recommendation: ship as-is for Sprint 1. The verdict is correct-by-construction and now visible. Treat user-adjustable hurdle rates (PHASE-03) as a fast-follow only if stakeholders want to stress-test the recommendation against their own covenants.

09 · Risks / Open Questions

What to watch

  • Manual UI verification outstanding: build + types pass, but the color-switch behaviour has not been exercised against a live GO and NO-GO run — do this before deploy.
  • Default hurdles are opinions: 12% IRR / 1.2 DSCR / 15-yr payback are reasonable defaults but not every investor's. PHASE-03 addresses this when needed.
  • Deploy packaging: the verdict depends on the model's reporting module being vendored at deploy; the deploy hook does this, but a hardened "fail loud if a subpackage is missing" check is worth adding (tracked under GAP-04 build hygiene).
  • Not yet live: users only benefit once the app is deployed (GAP-04).
