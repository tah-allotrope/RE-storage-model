What Is This Project?

This project is a Python simulation engine that replaces a complex Excel financial model used to evaluate a 40 MW Solar + Battery Energy Storage System (BESS) project in Vietnam, developed for Ecoplexus. The Excel model spans 13 sheets, 8,760 hourly rows, 25-year lifetime projections, and a VBA-driven debt sizing solver — all of which this Python engine aims to replicate with full auditability, testability, and reproducibility.

The model sits at the intersection of energy physics (battery dispatch, solar scaling), Vietnamese energy regulation (DPPA/CfD mechanism), and project finance (DSCR, IRR, NPV, debt sculpting). The Python engine will make it possible to run scenario analyses, stress tests, and audits that are impractical in Excel.

What Has Been Built — Detailed Walkthrough

Phase 1: Full Excel Model Audit

The 40 MW Solar + BESS Excel workbook was fully reverse-engineered. Every sheet was classified, every formula pattern extracted, and all cross-sheet data flows mapped. This produced three key artefacts: model_architecture.md, docs/analysis_report.md, and docs/besstoload_investigation.md. The audit also identified 7 risks in the Excel model (hardcoded values, circular references, DPPA toggle risk, battery augmentation timing). These documents form the authoritative blueprint for the Python implementation.

Phase 2: Python Implementation Specification

A detailed implementation_spec.md was written defining 13 Python modules across 7 layers. It includes exact function signatures, input/output types, formula-to-code mappings (e.g. Excel's LET() discharge logic → evaluate_discharge_permission()), and a Pydantic input schema. This spec means any developer can implement a module without touching the Excel file.

Phase 3: Core Layer — Type System & Exception Hierarchy

core.types defines 4 enums (StrategyMode, ChargingMode, TimePeriod, GridChargeMode) and 6 physical unit type aliases (PowerKW, EnergyKWH, Ratio, etc.). core.exceptions defines a 6-exception hierarchy all rooted at REStorageError, with structured attributes for debugging (timestep, imbalance_kwh, soc_kwh, etc.).

Phase 4: Physics Layer — Solar Module

physics.solar implements three functions (plus vectorized numpy versions of each): scale_generation() replicates Excel's Calc!Col F output scale factor; calculate_direct_pv_consumption() replicates Calc!Col I (MIN(Load, MAX(Solar-PV2BESS, 0))); and calculate_surplus_generation() calculates grid-exportable surplus. Full unit tests in test_solar.py.

Phase 5: Physics Layer — Battery Dispatch Engine

physics.battery is the most complex module — it replicates the entire Calc sheet LET() formula. It includes: BatteryConfig (frozen dataclass with all dispatch parameters), BatteryState (per-timestep output), calculate_pv_to_bess() with both TIME_WINDOW and PRECHARGE_TARGET modes, evaluate_discharge_permission() with 4 overlapping conditions (and a warning logger for conflicts, addressing Risk 1 from the audit), calculate_discharge_power(), calculate_grid_charge_power() with 3 grid charge modes, update_soc() with physics-correct efficiency application, and a top-level dispatch_single_timestep() that orchestrates all steps. SoCBoundsError is raised (not silently clipped) when dispatch logic over-charges or over-discharges.

Phase 6: Physics Layer — Energy Balance Validation

physics.balance implements the "Physics First" principle: before any financial calculation runs, energy must balance to within 1 Wh. Three validators: validate_energy_balance() checks Solar = Direct + Charged + Surplus; validate_soc_bounds() checks 0 ≤ SoC ≤ Capacity; validate_power_rating() checks power ≤ inverter/grid rating. All have vectorized numpy variants for processing full 8760-hour arrays in one pass. Full unit tests in test_balance.py.

In Progress: Input Layer — Pydantic Schemas

The SystemAssumptions Pydantic model is fully specified in implementation_spec.md with all field validators, but has not yet been implemented as actual Python code in the inputs/ package. The spec includes validators for capacity constraints, efficiency bounds (0.5–1.0), hour ranges, DPPA parameters, and financial parameters.

Not Started: Settlement, Aggregation, Financial Layers

The remaining 8 modules — DPPA/Grid settlement, monthly/annual/lifetime aggregation, and the financial waterfall with debt sculpting — have full spec but zero implementation. These are the commercially critical modules that produce the IRR and NPV outputs.

Key Risks Identified in Excel Model (Must Be Addressed in Python)

High

Circular Reference in Debt Sizing (Financial sheet)

The VBA GoalSeek creates a circular dependency: Debt Size → Debt Service → DSCR → Debt Size Check → Debt Size. If iterative calculation is off or VBA fails silently, the debt size is stale. Python replacement must use scipy.optimize with explicit convergence checks.

Med

Discharge Strategy Condition Overlap (Calc!Col J)

4 overlapping discharge conditions (when_needed, after_sunset, optimize_mode, peak) are OR'd together. Multiple conditions can fire simultaneously, causing unexpected off-peak discharge. The Python battery module already logs warnings for this — but the strategy logic itself needs explicit priority ordering.

Med

DPPA Activation Toggle (DPPA!Col F)

A single flag Does_model_is_actived?=0 silently zeros all DPPA revenue without error. In Python, the settlement module must validate that DPPA revenue is non-zero when the DPPA module is enabled, and raise an InputValidationError otherwise.

Med

Battery Augmentation Reset at Years 11 & 22

Loss!Col F resets battery capacity factor to 0.9745 at years 11 and 22 (implying full cell replacement). This assumes 100% restoration, not the typical 20–30% partial augmentation. The Python lifetime module must allow configurable partial augmentation percentages and validate that augmentation cost in the financial model matches the year schedule.

Low

Loss Table Year Coverage

If Loss!Col A doesn't span years 1–25, XLOOKUP silently returns 0, making projected generation drop to zero. Python's DegradationTableError exception is already defined to catch this — the lifetime module must validate coverage at load time.

Summary

The project is in a solid foundation phase. The hardest architectural decisions are made and documented. The physics engine — which is the most complex part of the simulation — is fully implemented and tested. The remaining work is largely mechanical: implement the higher-level modules (settlement → aggregation → financial) following the spec, then validate end-to-end against the Excel numbers.

The biggest risk to timeline is the DPPA settlement layer, which requires careful interpretation of Vietnam's CfD mechanism (k_factor, Kpp, Delta parameters), and the debt sizing module, which must replicate Excel's VBA GoalSeek correctly using scipy. Both have detailed specs. Neither requires new research — just implementation.
